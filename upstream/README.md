# 上游原始文件

这个目录里的文件**原样复制**自 MrTangLuyao 的 [Bilibili 线程撕裂者](https://github.com/MrTangLuyao/Bilibili-thread-ripper)，只作对照和溯源用，脚本并不直接加载它们。

- 上游版本：`0.9.4.0`
- 上游提交：`ee8709161e5a04cce2260a2937835e37f91ebcfb`（2026-09-22，合并 `#25 live-ripper`）
- 上游许可：MIT，见本目录下的 `LICENSE`

| 文件 | 移植到本仓库的内容 |
| --- | --- |
| `range-core.js` | Range 头与 Content-Range 的解析规则、区间切分算法、B 站媒体主机的判定正则、设置项的默认值 |
| `cdn-resolver.js` | 大陆与海外 CDN 主机列表、把签名地址换到别的节点的方法、节点健康记录和退避策略 |
| `idm-downloader.js` | 每块子区间必须校验 206 状态、Content-Range 与长度才能接受，失败后换节点重试、按节点速度分配的思路 |

移植时改掉的地方：Shadowrocket 的脚本环境没有 `URL`、`fetch`、`AbortController` 和流式读取，这些都换成了正则解析和 `$httpClient` 回调；每个分片请求都是一次独立的脚本运行，节点健康改用 `$persistentStore` 跨运行保存。

## 跟到 0.9.4.0 时的取舍

上游 0.9.4.0 的改动大多是网页播放器那一侧的事，代理里没有对应物：

| 上游的改动 | 这边怎么办 |
| --- | --- |
| 自动线程数（8 → 32 的阶梯，每次加线程都当作试验，十秒后没变快就退回） | 暂缓。阶梯的前提是同一个页面里能连续观察下载速度；这边每个分片是一次独立运行，而且脚本环境总共只允许约 20 条并发，现在的瓶颈是撞上这个上限而不是线程开得不够 |
| 落败副本被掐断时用已收字节算速度（`sample()`，上游注释说「没有它，慢节点永远测不到」） | 已移植成另一种形态：这边的请求无法取消、也读不到已收字节，改为在**开副本的那一刻**给还没回来的那个节点写一个速度上界。解决的是同一个问题——不让慢节点永远测不到 |
| 节点测速记录 90 秒过期 | 已移植：单块测量 90 秒、整段实测 2 分钟（原先是 10 分钟和 5 分钟，一次侥幸的快样本能统治十分钟） |
| `assignPrimaries` 把慢于最快节点 1/12 的节点整个剔出候选 | 未单独移植：这边一段只用一个节点，1.5 倍的换人门槛已经覆盖了同样的效果；把淘汰规则套在候选池上反而会把「试探一个没测过的节点」这条发现通道一起干掉 |
| 服务器返回 412 / 429 时退一档并让这一档休息三分钟 | 已移植：这两个状态码不再按“节点坏了”封五分钟，只短暂退避该节点，同时三分钟内所有请求的线程数减半 |
| 直播加速（节点池竞速 + 提前缓存 playlist 里的全部分片） | 不适用：那是网页直播播放器的 HLS 分片，App 的直播流不走这条路 |
| 拖进度条留在当前播放会话内、挡住 B 站内核的回跳、停住内核自己的下载调度器、杜比 / Hi-Res 音轨的识别、缓冲区满时留段等待 | 不适用：都要握着 `<video>` 和 MediaSource，代理碰不到播放器 |
| 子块大小跟随实测连接速度在 64 KiB 到 1 MiB 之间自动调整 | 不适用：上游的公式里 `区间长度 / 线程数` 这一项在 1 MiB 的区间上永远压过 `0.6 × 单连接速度`，算下来恒等于现在的固定值。它只在上游那种「一次要几 MB 到几十 MB」的场景才起作用，而 App 的区间被钉死在 1 MiB |

更新上游文件时，把新版本复制过来并改这个说明里的版本和提交号，再对照差异同步 `src/` 里的移植。
